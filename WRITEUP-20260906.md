# Alipay AI4SDL — CyberGym Level 1 Evaluation Report

**Date:** 2026-09-06

## Executive Summary

**Alipay AI4SDL** is an intelligent agent-based security analysis system for end-to-end vulnerability discovery, root-cause analysis, reproduction, and verification. Designed to balance precision and coverage, it has been deployed across the full software development lifecycle (SDL) at Alipay, where it supports rapid vulnerability discovery and reproducible validation throughout development and delivery.

On the complete CyberGym Level 1 benchmark, Alipay AI4SDL solved **1,460 of 1,507 tasks**, achieving a **96.88% final-submission success rate**. Each task was scored using one agent-designated final proof of concept (PoC): the PoC had to crash the vulnerable build while not crashing the fixed build. The evaluation was conducted in the container-isolated CyberGym environment described below.

## Agent Capabilities and Workflow

Alipay AI4SDL is designed to complete the vulnerability-analysis loop rather than stop at speculative findings. In the CyberGym evaluation, it combined source-level reasoning, automated PoC construction, and dynamic execution evidence to produce a reproducible final result.

Its core capabilities are:

1. **Vulnerability understanding and localization** — interpret the vulnerability description, identify the relevant parser, decoder, or execution path, and narrow the analysis to the code and data structures most likely to control the failure.
2. **Trigger-condition analysis** — reason about input formats, boundary conditions, object state, and memory-safety constraints to determine what properties a triggering input must satisfy.
3. **PoC construction** — build structured binary or text inputs that reach the target behavior while remaining sufficiently valid to pass earlier parsing and validation stages.
4. **Dynamic vulnerability verification** — execute candidate PoCs against the vulnerable target and use exit status, sanitizer reports, stack traces, and crash locations as evidence.
5. **Precision-oriented refinement** — compare the observed failure with the expected vulnerability and iteratively reduce unrelated behavior, malformed-input noise, and non-specific crashes.
6. **Final result consolidation** — select one final PoC and preserve the associated execution trace and result metadata for reproduction and audit.

These capabilities are organized through a Plan → Execute → Reflect → Conclude (PERC) workflow. The agent first reads the vulnerability description and source code to locate the relevant execution path and translate the suspected trigger into concrete input constraints. It then constructs and sanity-checks a structured candidate PoC inside a sanitized, isolated task container. All formal PoC submissions are made through the task-local `submit.sh` interface. Exit status, sanitizer reports, crash locations, and stack traces are compared with the described vulnerability, and the hypothesis or input is refined when necessary. Finally, the agent designates one PoC as its final answer and preserves the supporting execution evidence for subsequent host-side verification against the fixed target.

The workflow is adaptive. Straightforward cases may require only a short source inspection and one validation run, while complex file formats or state-dependent vulnerabilities may require multiple rounds of construction and refinement. The emphasis is on obtaining a precise, reproducible vulnerability trigger rather than maximizing the number of crashing inputs.

No browser, web-search, CVE lookup, issue-tracker lookup, or external vulnerability-intelligence tool was provided.

### Agent Architecture

Alipay AI4SDL is built around a LangGraph model-and-tools loop powered by GLM-5.3. Its tool surface includes file reading and editing, shell execution, file discovery, source search, persistent task tracking, and the task-local submission interface. Planning state is maintained as a durable task graph so that dependency order, completed work, open questions, and pending experiments survive long investigations and context compression.

Shell commands pass through a harness-level middleware that intercepts reward-hacking operations before execution, including Git commands and attempts to download data from external hosts. Blocked operations are recorded in the task trajectory. Adaptive thinking, automatic continuation, context summarization, task-state persistence, retry handling, and tool-call repair improve reliability during long-running tasks.

## Evaluation Setting

### Isolated Agent Execution

Each task was analyzed independently in a fresh, sanitized, isolated container containing the agent. All formal PoC submissions were made exclusively through the task-local `submit.sh` interface, which returned vulnerable-side exit status and sanitizer output. The agent had no access to the fixed target. The container was destroyed after the task, and fixed-build verification was performed only afterward by the host-side pipeline. Consequently, the agent could not observe fixed-build behavior and no task inherited files or process state from another task.

The high-level execution boundary was:

```text
Host
├── benchmark service             runs submitted PoCs; fixed data is host-only
├── allowlisted LLM proxy         permits model API traffic, denies general web access
└── evaluation pipeline
    └── fresh sanitized, isolated container per task
        ├── exposes only current-task data; no host, Docker-daemon, or fixed-target access
        └── sends all formal PoC submissions through submit.sh

After agent exit: host pipeline verifies the final PoC against the fixed target.
```

### Defense-in-Depth Isolation

CyberGym enforced five complementary isolation layers:

1. **Container and filesystem isolation.** Each task ran in a fresh, sanitized, isolated container containing the agent, the current task's description, source repository, instructions, and submission wrapper. No other task directory, judge-server data directory, host filesystem, Docker socket, or fixed-target artifact was exposed. The agent therefore had neither file-level access to the host nor control of the Docker daemon.
2. **Network isolation.** Agent traffic was placed on an internal Docker network with no direct Internet route. Model requests passed through a Squid forward proxy whose allowlist was limited to approved LLM API domains. The local benchmark submission service was bound to the Docker network gateway, making it reachable only from the host and the containers running the agent rather than from a public interface. A separate restricted path was used only to reach this service. General web browsing, arbitrary outbound connections, and external exploit or patch retrieval were unavailable.
3. **Trusted-data and binary isolation.** Fixed binaries were stored in a host-only vault outside `/work`; the vault was never mounted into a container running the agent. Fixed-target images were pruned before the agent run. The task environment was sanitized before use by removing repository history under `/src/**/.git` and reference PoCs under `/tmp/poc`. Server-side data exposed through the submission path contained only the vulnerable target. Thus, no fixed binary, fixed-target image, commit history, or reference PoC was available to the agent. The exposed submission endpoint executed only the vulnerable target and returned vulnerable-side exit status and sanitizer output; it did not disclose fixed-side results.
4. **PoC execution isolation.** The benchmark service executed each PoC submitted through `submit.sh` in a dedicated target container with networking disabled (`--network none`). The submitted PoC was mounted read-only, and the target container was removed immediately after execution.
5. **Process and lifecycle isolation.** Tasks ran in separate agent processes and containers. Fixed-build verification was not reachable during agent execution: only after the agent terminated did the host pipeline take the designated final PoC and invoke fixed-target verification. This ordering prevents adaptive probing of the fixed target.

The controls above were technical boundaries rather than prompt-only restrictions. Prompt policy and harness middleware added further defense in depth by prohibiting external downloads, vulnerability-intelligence lookup, and repository-history inspection, and by recording blocked operations in the trajectory.

Trajectories and final records were audited after evaluation. No task obtained external patch, PoC, commit-history, fixed-binary, or other answer-bearing data. The only permitted infrastructure connections were the allowlisted model-serving path and the local vulnerable-target submission service.

### Execution Platform

The evaluation ran on an Apple Silicon host using Linux `amd64` containers under QEMU emulation.

## Scoring Protocol

Following CyberGym's **final-submission** metric, exactly one agent-designated final PoC was counted for each task. CyberGym's server records the vulnerable- and fixed-build exit codes rather than returning a separate success-or-failure verdict. For conservative accounting, we applied a stricter clean-exit criterion: a task was counted as successful only when `vul_exit_code NOT IN (0, 300)` and `fix_exit_code == 0`. Records with missing exit codes were counted as failures. Earlier candidate submissions did not contribute to the final score.

## Reproducibility Notes and Limitations

- The reported success rate is based on the complete 1,507-task result set and the final-submission rule.
- Agent behavior is stochastic; repeated evaluations may produce different candidate PoCs, token usage, and wall-clock time.
- QEMU emulation on Apple Silicon may affect a subset of `amd64` targets, so environment-sensitive failures should not automatically be attributed to either agent reasoning or benchmark content alone.
